# SableEdit

Drop-in SVG element editor (paths first). No runtime dependencies.

Press a shape to select it (it opens in **scale** mode). Drag anywhere on the selected shape to move it; click or tap it again without dragging to switch between **scale** and **rotate/skew**. **Double-click** a shape (or **long-press** it with a finger or pen) to enter its own **edit** mode, the shape's own controls; **Esc** steps back: edit mode to scale, then deselect. The handles show which mode you are in. Hosts can call `ed.edit()` to do the same, and `ed.mode = 'scale'` also leaves edit mode.

In a path's edit mode, click a node or a segment to select it (Shift adds or removes; clicking the selected segment again clears it; a double-click on the stroke adds a node). Only the bezier and arc handles that belong to the selection are drawn: a node brings the handles of the two segments that meet at it, a segment brings its own. Dragging a selected node moves every selected node. **Delete** / **Backspace** removes selected nodes (the neighbours join up) or cuts the path at selected segments (a closed path opens); **Escape** clears the selection. A path whose last point sits on its first (closed with a Z that adds no line, or not closed at all) has a single *joined* node there: one square, and moving, deleting or setting the type of it takes both halves along, with the handles on either side pairing up as at any other node. A Z that really draws a line is a segment of its own and the nodes at its ends are independent. Polygons and polylines get node selection, multi-move and delete too. Hosts that attach with `keys:false` can call `ed.deleteSelection()` / `ed.clearSelection()` and read `ed.selection`.

A node with a segment on each side has a type, worked out from the geometry (where a side is a line or an arc, from its tangent): **corner**, **smooth** (the handles stay on one line through the node, each keeping its own length) or **symmetric** (mirror images, written as `S` / `T` in the path data and kept that way when the path is rewritten). Dragging a handle keeps its node as it is: the other handle of a smooth node swings to stay opposite, a symmetric node's mirrors. Hold **Shift** while dragging to make the node symmetric, or **Alt / Option** to move the handle on its own and make it a corner. Right-click a node for **Node type > Corner / Smooth / Symmetric**, which also works on a multi-node selection and on nodes between any segment types. Smooth and Symmetric always leave a node with handles to drag: they go on the line through the node that is perpendicular to the bisector of the angle the two segments make there (the average of their two tangents), so neither side is the one that has to follow the other. A handle that already has a length keeps it (Symmetric then gives both the average of the two); a handle that is missing or retracted into the node (a line becomes a bezier of the other side's kind, a curve end that was only clicked) gets half the distance to the node at the other end of its segment (Symmetric: the other handle's length if there is one, else half the average of the two distances). Arcs can't turn, so beside an arc the arc's tangent is the one that stays: Smooth turns a line into a quadratic along it and a bezier's handle follows it, and Symmetric turns a line into the circular arc tangent there, or an arc beside a bezier into a bezier. Two arcs become single best-fit cubics (a big arc comes out approximate; no nodes are added). A quadratic has one control for both its ends, so where that would unsmooth the node at its far end the segment becomes a cubic instead. A closing line that draws something is made a segment of its own first (the start and end then join); a cubic that runs from its node back to itself smooths against itself. The ends of an open path have one side only and no type. Smooth nodes are drawn with rounded corners and symmetric ones as circles.

Right-click a segment for **Segment type > Line / Quadratic curve / Cubic curve / Arc**; the converted segments stay selected so a line turned into a curve can be shaped straight away. Quadratic to cubic is exact, cubic to quadratic and curve to arc are best fits (an arc is fitted through the curve's midpoint), a line becomes a straight curve or an arc tangent to the segment before it (a one radian arc when there is none), and an arc of more than a quarter turn becomes several curves. Lines are written as `H`, `V` or `L`, whichever is shortest, for the segments an edit touches; the rest of the path keeps the commands it had.

**Converting shapes:** right-click a shape (or the handles of the selected one) for **Convert to > Path / Rectangle / Circle / Ellipse / Line / Polygon / Polyline**, whichever of those make sense for it (`ed.convert([el,] 'path')` does the same from code and returns the new element; `ed.convertTargets()` lists the choices). Everything can become a path, exactly: lines as H / V / L, circles and ellipses as four arcs (`{arcs: false}` for cubics), rounded corners as arcs. A path is the stepping stone to the rest, and where it really is the target it is recognised: an axis-aligned rectangle becomes a rect, arcs once round one centre become an ellipse or circle (so circle -> path -> circle round-trips), polygon <-> polyline keeps the closing edge, a one-segment path becomes a line, and a fully rounded rect IS an ellipse. Where it is not, the menu says *(approx.)*: curves flatten into polygon / polyline edges within a small tolerance (`{tol}`), a path or polygon becomes the rect or ellipse of its bounding box, and a circle from a rect or ellipse keeps the area (r = sqrt(rx * ry)). Not offered: anything but a one-segment shape as a line, a line as a rect / circle / ellipse, a path with several subpaths as a polygon / polyline. Other attributes (id, class, style, fill, transform...) come along. A new tag is a new element, so a conversion is one undo step, the selection and its mode carry over to the replacement, and `ed.on('convert', ({el, from}) => ...)` (or the `onConvert(el, from)` option) tells a host that the element it knew is gone.

**Creating shapes:** right-click (Ctrl-click on a Mac) anywhere on the canvas for the context menu, then **Switch Tool**: the tool stays armed until you choose Pointer (or press Esc). Built-in tools: **circle** (press for the centre, drag out to the radius), **rectangle** (press one corner, release on the opposite one), **ellipse** (the same, for its bounding box), **line** (press the start, release at the end) **path**, **polygon** and **polyline**, the pens. **A tool is also its shapes' edit mode.** Arming a tool keeps a selected shape of its kind (in edit mode: a rect's corner and radius handles, a circle's radius, a path's nodes ...), and a press on a shape of that kind edits it instead of drawing over it: for a rect, circle, ellipse or line its body, for the pens (path, polygon, polyline) its stroke only, the fill being where a new one starts (hold **Alt** to start a new shape wherever you press). Anywhere else a press draws, and the new shape is selected, ready to be adjusted before the next. Esc leaves the tool with the shape still selected (in the mode it was in before). Edit mode and the tool are one state: a double-click (or a long touch) on a shape arms its own tool, `ed.edit()` and `ed.mode = 'edit'` do the same, and `ed.mode = 'scale'` / `'rotate'` or Esc leave it. While a tool is armed, a click that draws nothing selects the shape of another kind it lands on (and leaves the tool) or, on empty canvas, deselects. Every point a tool is given is put on the policy's snap grid and kept inside its bounds (a circle's whole radius, too). The pens' special gestures, pressing the other end of a path to close it and clicking the end node to finish, apply once you have added a node; before that a path is just being edited, and Esc clears the node selection first. Drawing and editing are separate permissions: the policy's `create` says which tools may draw (`ed.tools` reports it per tool), and a tool still arms, to edit only, while a shape of its kind can be edited. The menu is the only UI the widget needs, so it works in pages with no toolbar; `ed.tool`, `ed.addMenu(fn)` and `ed.penSegment` are there for hosts that want their own.

**The pens (Path, Polygon, Polyline):** it lives across many presses, and it is the path editor with the pen switched on (the same handles, node types and Segment type menu), so a path can be edited at every step before the next node is added. *Rule: the pen continues from the selected node of the selected path, if that node is an endpoint; with no endpoint selected a press starts a new path.* A press on empty canvas adds a node after it (a line), a press-drag pulls handles instead (the node is symmetric, written as `S`; Alt-drag breaks it). The new end node is selected, so its handles are there to edit and the next press continues from it. Pressing the *other* end of the path being drawn closes it (from two nodes on: a quadratic or an arc closes into a balloon, and a drag on that press shapes the closing segment); clicking the end node again, double-clicking it, **Enter** or right-click > **Finish path** finishes (the path stays selected, no node does, so the next press starts a new path). **Esc** leaves the pen (the path stays selected, in scale mode); a second Esc deselects. Continuing from a path's first node reverses the path first. Right-click > **Next segment** makes the next node a line, a quadratic, a cubic or an arc (a drag then sets the control point, or bends the arc through the pointer); `ed.penSegment` does the same from code. With a mouse a dashed rubber band shows the next segment; without hover (touch) tap adds a node and drag pulls its handles. Every node is an undo step of its own, and a path left with only its first node is thrown away. The policy applies to every node: it needs `geometry.edit` and `nodes.insert`, new nodes are put on the snap grid and inside the bounds, and a path with any pin is not extended (`denied`, reason `pinned`).

**Polygon and polyline pens** work the same way on vertex lists: a press adds a vertex, and a drag moves it until you let go (there are no handles). A polyline grows on the end the selected vertex is on, and from its first vertex it grows in front; a polygon has no ends, so the new vertex goes right after the selected one. Clicking the vertex the pen is on again, **Enter** or right-click > **Finish polygon / polyline** finishes, and Esc leaves the pen, as for paths. A polygon with fewer than three vertices, or a polyline with fewer than two, is thrown away when the pen leaves it. The policy applies as for paths (and every vertex is put on the snap grid and inside the bounds).

## Permissions
By default every shape matching `selector` is fully editable. Pass a `policy` to say exactly what a viewer may do to which shape. Nothing is allowed until a rule grants it, and later rules override earlier ones:

    SableEdit.attach(svg, { policy: [
      { select: '.logo',  can: ['geometry.edit', 'attrs.edit'], attrs: { deny: ['stroke*', 'style'] } },  // reshape it, but not stroke or style
      { select: '.curve', can: ['geometry.edit', 'nodes.*'], pin: ['endpoints'] },                         // any node but the ends
      { select: '.fixed', can: ['transform.*', 'geometry.edit'] },                                         // no adding or deleting nodes
      { select: '#bg',    can: [] },                                                                       // not selectable
      { select: '.card',  can: 'all', bounds: { x: 0, y: 0, width: 600, height: 400 },                     // keep it on the card,
        ranges: { r: [5, 50], 'stroke-width': [1, 8] } },                                                  // and keep sizes sane
    ]});

Capabilities: `transform.move|scale|rotate|skew`, `geometry.edit` (the edit mode), `nodes.insert|delete`, `attrs.edit` (fill, stroke, style, class... narrowed by `attrs.allow` / `attrs.deny` globs), `element.convert` (change the shape into another kind; the new element must still be selectable and allow `geometry.edit` under your rules, a `pin` on either refuses it, `ranges` clamp it, `bounds` are not allowed to be exceeded further than the old shape did, and `snap` is not applied; `'all'` includes it, so list capabilities explicitly where conversion should stay off). `pin` locks nodes (`'endpoints'` or indices) and, because moving or scaling would drag a pinned node along, turns that shape's transforms off. Disabled modes and handles aren't offered, and every write is checked too, so `ed.set()` is held to the same rules (`ed.set(el, attr, val, src, { force: true })` is the escape hatch for host code; `ed.can()` / `ed.canSet()` let a host grey out its own controls; `onDenied` / `ed.on('denied')` report refusals). `bounds` is a box in the shape's parent coordinates that its nodes (a path's anchors *and* bezier handles, a polygon's vertices, a rect's corners, an ellipse's extent) may not leave: a dragged node stops at the wall and slides along it, a move stops at the wall, a resize keeps its far edges, and a scale or rotation that would cross it is refused. `ranges` clamp numeric attribute values (`r`, `width`, `stroke-width`, and the same properties inside `style`). `snap` puts whatever an edit moves on a grid (`snap: 10`, or `[10, 5]` for x and y): path anchors and bezier handles, polygon vertices, rect edges, line ends and circle/ellipse centres and radius edges. It acts on the stored numbers, only on what the edit changes, and moves a shape (or a node together with its handles) by one amount, so curves aren't bent; it is forced, not a toggle. Order of precedence: snap, then pins, then ranges, then bounds. `ed.range()` / `ed.bounds()` / `ed.snap()` tell a host UI the limits, and `ed.setMany()` writes several attributes as one checked, undoable step. The policy guards the person using the widget, not the page: for a real guarantee run `checkWrite()` from `src/policy.js` (pure, Node-safe) on the server. See the header comment in `src/banner.txt` for the full rule syntax.

### Permissions in markup
For a static page with no JS config, write the rules on the shapes themselves and list `'markup'` in the policy (`policy: 'markup'`, or `policy: [{ select: '.edit', can: 'all' }, 'markup']` to mix with rules; later entries win):

    <svg ... data-sable-policy="transform.move">                      <!-- default for the whole drawing -->
      <path data-sable-policy="geometry.edit, nodes.*; attrs-deny: stroke*, style; pin: endpoints" .../>
      <g data-sable-policy="geometry.edit; -nodes.delete; bounds: 0 0 600 400"> <circle data-sable-policy="range: r=5..50" .../> </g>
    </svg>

Clauses are separated by `;`: bare words grant capabilities (`-name` takes one away; `can:` / `cannot:` spell it out), `attrs-allow:` / `attrs-deny:` (globs), `pin:`, `bounds: x y width height`, `range: name=min..max` (either end may be empty), `snap: 10` or `snap: 10 5`. Declarations on a `<g>` or the `<svg>` cover what's inside, and the nearest one wins. Markup is only read when `'markup'` is in the policy, so SVG uploaded by your users can't grant itself powers: enable it only for markup you wrote. A typo throws when the editor attaches. The attribute can't be changed through the editor itself.

## Using it
Plain script tag (defines `window.SableEdit`):

    <script src="dist/sable-edit.js"></script>
    <script>const ed = SableEdit.attach(document.querySelector('svg'));</script>

ES module:

    import { attach } from './dist/sable-edit.esm.js';

`dist/sable-edit.min.js` is the minified script-tag build. See the header comment in `src/banner.txt` for the full API.

## Developing
Node is for development only (unit tests, build, local server); the shipped files in `dist/` need nothing.

    npm install
    npx playwright install   # one-time, for e2e tests
    npm run serve            # builds, then serves http://localhost:8080/demo/
    npm run test:unit        # pure logic (node:test), no browser
    npm test                 # unit + e2e (Playwright)
    npm run build            # src/ -> dist/

## Layout
- `src/` ES module source. `path-math.js` is pure (no DOM) and unit-testable in Node.
- `src/policy.js` permissions: compiles a policy and decides writes (pure, no DOM, unit-tested in Node).
- `src/tools.js`, `src/tools/` creation tools (a registry like the widgets', one file per tool); `src/menu.js` the context menu UI.
- `src/pen-math.js` the pens' arithmetic (pure, unit-tested): a path's endpoints, reversing a subpath, adding a node, closing; adding a vertex to a polygon / polyline. The pens' UI is the path and polygon / polyline widgets' pen mode.
- `src/widgets/` one file per widget family. `transform.js` (scale and rotate/skew layers) and `halo.js` (an invisible fat outline that keeps thin shapes grabbable) are generic; `src/body.js` is the press-to-move / click-to-switch-scale-and-rotate gesture; the rest are per-shape *edit mode* widgets. Registration order matters (see `src/index.js`): the registry returns the first match, so the catch-all fallback is imported last.
- `dist/` built output, committed so the demo works without a build step.
- `demo/` widget demo page, loads `dist/sable-edit.js`.
- `test/unit/`, `test/e2e/`
